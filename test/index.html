01 / How to use this guide

  1. Ask the project owner for the approved test URL, build/commit and separate test accounts. Use staging or an isolated local environment. The live domain is https://enroutelogtek.in; do not assume permission to test production.
  2. Fill in the run details below. Run the main journey first, then negative, permission and boundary tests.
  3. Open a case, perform its steps and record what actually happened. A checkmark in the build tickets is not test evidence.
  4. Select Passed, Failed or Blocked. Passed and Failed require an actual result and an evidence reference or attached screenshot. Blocked requires the reason. Click Save case result.
  5. Use Download completed HTML before closing this tab. The downloaded copy contains saved results and attached screenshots. Changes are held in memory until downloaded; editing the original file does not automatically save progress.

Use synthetic data and test inboxes. Do not enter passwords, OTPs, tokens or real company documents into this report. Redact screenshots before attaching them. Cross-company, upload/delete, race and service-failure tests are staging-only and require the owner's approval.

03 / Current rules to verify

Roles and visibility

  • Network changes: admin and co-admin. Other roles may read.
  • Load management and bidding: admin, co-admin and bid_manager, on the appropriate company side.
  • Transporters see their own attempts and rank, never competitors' identity, prices or the customer's hidden target.
  • Platform administration belongs to root_admin only.

Ad hoc defaults

  • Five bid attempts per transporter per load.
  • Default bid window: 12 hours; acceptance: 24 hours.
  • Pickup at least two hours ahead; bidding ends before pickup.
  • Lowest amount ranks first; equal amounts favour the earlier attempt.
  • Only closed loads can be awarded. A customer may choose a non-lowest bid.
  • Cancel: draft/live/closed/expired. Extend: live/expired. Edit: draft only.

Draft → Live → Closed → Awarded → Accepted → In execution → Completed

Branches: no bids → Expired; permitted cancellation → Cancelled; declined or expired award → Closed. Optional no-bid auto-extension runs once when time before pickup permits. These are implemented defaults, not confirmation of the nine unanswered client decisions in the tickets.

04 / Feature test checklist

P0: access control, data privacy or the main business journey. P1: important workflow, validation or resilience. P2: presentation and convenience. A failed P0 blocks sign-off. An applicable P0 that is Blocked or Not tested also prevents full sign-off.

05 / Known gaps and tests likely to expose defects

These are source-review findings and product limitations, not results of this tester's run. Reproduce on the exact build and record evidence. Do not mark a security requirement Passed because the current code lacks the check.

  • Document access: upload and delete routes currently lack authentication/ownership checks. SEC-02 and SEC-03 are expected to reveal a release-blocking issue until fixed. Onboarding may need a registration-scoped identity rather than a normal logged-in session.
  • Registration ownership: submission takes a company ID without a registration ownership guard. Check SEC-04 against synthetic companies only.
  • Session renewal: verify expired-access-token handling and that an old logged-out token stays invalid after a fresh login. Check AUTH-08 and SEC-05.
  • Abuse protection: rate limiting is not evident in the reviewed auth routes. SEC-06 requires an agreed staging request ceiling; no uncontrolled traffic.
  • Multiple trucks: a load can request multiple vehicles, but the award stores one vehicle and driver. OPS-05 records this limitation. A passing single-truck assignment does not validate multi-truck execution.
  • Delivery: completion is a customer action, not verified per-truck POD processing. Full trips, POD verification, RFQs/contracts, fleet allocation, fleet/driver management, earnings/reports, team management and subscription checkout/enforcement are not complete. Test placeholder honesty, not imaginary workflows.
  • Company profile: GET/PATCH /companies/me handlers are TODOs. Do not sign off company settings as operational; record a bounded timeout if checking these handlers.
  • Files and concurrent changes: JPEG extension handling and state changes made at the same time need focused regression tests. Do not hide these failures behind general happy-path success.

06 / Evidence, defects and tester handoff

  1. Name evidence CASE-ID_browser_viewport_YYYYMMDD_result.png, for example BID-02_Chrome_1440x900_20261110_fail.png. Include the relevant state and redacted request/response if needed.
  2. Attach a redacted PNG, JPEG or WebP screenshot to a case, up to 2 MiB each. Attachments are embedded in the downloaded HTML. For many images, keep the HTML small by using evidence filenames and delivering a separate evidence folder through the owner's agreed channel.
  3. For a failure, record: steps and IDs used, expected result, actual result, reproducibility, severity and a bug reference. Never attach cookies, tokens, full credentials or private documents.
  4. For a blocked case, identify the missing account, permission, fixture or service. A blocked test is not a pass. For an unavailable browser or service, record Blocked rather than guessing.
  5. Retest fixes on the new build, with original failure evidence retained in the bug tracker. Update the report's build and distinguish fresh runs from earlier evidence.
  6. Download the completed HTML and reopen that copy to confirm results and screenshots survived. Send that file and any referenced evidence to the owner. Sharing the original unmodified file will not include your saved run.

Sign-off: all applicable P0 cases must pass; no unresolved access-control or data-loss defects; remaining P1/P2 failures need explicit owner acceptance. The owner, not this document, approves release. This workbook only counts manually saved results and does not execute application tests.
